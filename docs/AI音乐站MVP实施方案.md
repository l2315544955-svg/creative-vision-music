# AI音乐站 MVP 实施方案

## 1. 项目目标

本项目的优先级不是“功能尽可能多”，而是“快、准、狠”：

1. 先做出一个可以稳定生成音乐、接近 `suno.cn/create` 主流程体验的前台站点。
2. 后端作为本项目独立实现，账号、组织、点数和代理能力如需参考，只从现有 `ruoyi` 项目中复制可用代码到本项目再调整优化。
3. 收费先跑通最短路径，再扩展会员、资源包和多层级组织结算。

## 2. 已验证结论

### 2.1 目标页的主要交互能力

通过抓取 `https://www.suno.cn/home/#/create` 的页面资源，可以确认目标页至少包含这些创建侧能力：

- 模型选择
- 音乐风格输入与风格标签选择
- 歌词相关模块
- 从已有歌曲某个时间点继续生成
- 歌手性别选择
- 参考音频/上传音频相关能力
- 多个音乐模型族而不只是 Suno

从页面资源中还能看到目标页存在以下模型值：

- `chirp-v3-0`
- `chirp-v3-5`
- `chirp-v4`
- `mureka-7.5`
- `mureka-7.6`
- `mureka-o2`
- `mureka-8`
- `music-2.5`
- `music-2.5+`
- `udio32-v1.5`
- `udio130-v1.5`
- `chirp-auk`

结论：

- 目标页的“创建体验”不是单一 Suno 接口页，而是一个多模型音乐创作工作台。
- 如果第三方文档只覆盖 Suno 接口，那么“完全 1:1 复刻所有模型能力”当前并不现实。

### 2.2 AIZNT 文档已明确支持的音乐能力

来自 `https://aiznt.apifox.cn/llms.txt` 及对应文档，当前明确可实施的音乐能力比上一家更完整：

1. Suno 生成歌曲
   - 接口：`POST /suno/submit/music`
   - 支持灵感模式与固定自定义歌词模式
   - 支持纯音乐
   - 支持续写：`task_id`、`continue_at`、`continue_clip_id`
   - 支持上传生成、Cover、Replace Section、Persona、上传续写等高级场景文档

2. Suno 生成歌词
   - 接口：`POST /suno/submit/lyrics`
   - 输入 `prompt`，返回歌词任务 ID

3. Suno 查询结果与二次处理
   - 接口：`GET /suno/fetch/{task_id}`
   - 结果可直接拿到 `audio_url`、`image_url`、`clip_id`、`duration`、`model_name`
   - 同时提供：
     - `音轨分离`
     - `获取 wav 格式`
     - `Timing: 歌词、音频时间线`
     - `批量查询任务`
     - `批量查询歌曲`

4. Udio
   - 文档已公开：
     - `POST /udio/generate-proxy`
     - `查询音乐任务`

5. Minimax 音乐
   - 接口：`POST /minimax/v1/music_generation`
   - 明确支持：
     - `music-1.5`
     - `music-2.0`

结论：

- AIZNT 在“音乐能力显式暴露”上明显强于上一家，不再只是一个模糊的 Suno 代理文档。
- 其能力集合已经足够支撑我们做一个“先以 Suno 为主、再扩到多模型”的音乐工作台。

### 2.3 AIZNT 文档中的风险点

这家文档虽然更完整，但仍有三个实施风险：

1. Suno 版本与计费口径不是一一映射
   - 参数文档明确给出了：
     - `chirp-v3.0`
     - `chirp-v3.5`
     - `chirp-v4`
     - `chirp-auk`
     - `chirp-bluejay`
     - `chirp-crow`
   - 但登录后价格接口里显示的是通用 SKU：
     - `suno_music`
     - `suno_lyrics`
     - `suno_stem`
     - `suno_timing`
     - `suno_upload`
     - `suno_wav`
   - 这意味着前台展示模型版本时，后端仍然必须做可配置映射，不能把版本和价格硬编码绑死。

2. Udio 文档已公开，但当前账号未看到显式 Udio 定价行
   - 当前可见前端 vendor 列表里有 `Udio API`
   - 但本次登录账号的 `user models / pricing` 中没有看到 `udio32-v1.5`、`udio130-v1.5` 这类显式价格模型
   - 因此 Udio 可以视为“文档已支持、账号开通情况待确认”的能力

3. 目标页仍然存在供应商未完全覆盖的模型族
   - 当前还没有看到：
     - `mureka-*`
     - `music-2.5`
     - `music-2.5+`
   - 所以仍然不能承诺目标站全部模型 1:1 同步上线

## 3. 可落地范围判断

### 3.1 第一阶段可以快速实现的能力

这些能力已经有明确文档支撑，适合直接进入 MVP：

1. 创作首页 UI
   - 大输入框
   - 音乐风格标签
   - 标题
   - 自定义/灵感模式切换
   - 纯音乐开关
   - 模型切换先支持 `Suno / 海螺音乐`
   - 创建按钮

2. 歌词生成
   - 先调用 `/suno/submit/lyrics`
   - 再轮询任务结果
   - 生成后自动回填歌词框

3. 音乐生成
   - Suno 自定义模式：`prompt + tags + title`
   - Suno 灵感模式：`gpt_description_prompt`
   - Suno 纯音乐模式：`make_instrumental=true`
   - 海螺音乐：`music-1.5 / music-2.0`

4. 续写/继续创作
   - 选择已有作品
   - 指定 `continue_at`
   - 携带 `continue_clip_id`

5. 任务轮询与结果展示
   - 状态：排队中、处理中、成功、失败
   - 展示音频链接、封面、标题、时长

6. 我的作品列表
   - 最近任务
   - 生成中任务自动刷新
   - 成功作品试听、下载

7. 音轨分离与时间线能力预留
   - `suno_stem`
   - `suno_timing`
   - 首版可以先不前台化，但后台和接口层要预留

8. 组织版点数消耗
   - 在本项目内独立实现组织、配点与模型扣费规则
   - 如需提速，可参考 `ruoyi` 的现有逻辑并复制到本项目重构

9. 个人版点数消耗
   - 先做账户点数扣减
   - 支付先走最短实现

### 3.2 第二阶段再做的能力

这些能力不是不能做，而是现在不该挡住上线：

1. Udio 接入
   - 文档已经存在
   - 但当前账号下还没看到显式 Udio 定价模型
   - 建议作为二期或灰度能力

2. Suno 高级场景前台化
   - Cover
   - Replace Section
   - Persona
   - 上传续写
   - 文档已存在，但首版不应让 UI 复杂度失控

3. 歌手性别真实控制
   - 目标页有该 UI
   - 当前更稳的做法仍然是提示词增强，而不是先承诺真实可控

4. 1:1 社区、推荐流、歌手页、专辑体系
   - 这些不是 MVP 必需
   - 可以等生成链路和收费跑通后再补

5. 更完整的多模型音乐工作台
   - 目标页实际还包含 `Mureka / music-2.5 / Udio` 等更细粒度模型族
   - 当前并没有足够证据表明这些都能在现有账号下直接上线

### 3.3 当前不能承诺“完全复刻”的部分

以下内容在现阶段不能对外承诺 1:1：

1. 目标页全部模型能力
   - 因为当前明确可落地的是 `Suno + music-1.5 / music-2.0`
   - `Mureka / music-2.5 / music-2.5+` 仍未确认

2. Udio 当前账号侧的真实可用性
   - 文档公开了 Udio
   - 但当前账号模型广场里没有显式看到 Udio 价格行

3. 歌手性别、参考音频、多模型工作台的真实效果一致性
   - 因为文档侧没有足够接口证据

所以更准确的项目目标应该改成：

`第一阶段复刻 create 页核心工作流与主要视觉结构，并先上线 Suno + 海螺音乐 的可收费版本。`

## 5. 以 `ruoyi` 为参考源码的独立实现方案

### 5.1 可以参考并复制到本项目的能力

`/home/l0425/ruoyi/ruoyi-ai` 已经存在以下关键能力：

1. 组织入组与审批
   - `POST /auth/org/join`
   - `POST /auth/org/join/approve`
   - `GET /auth/org/join/pending`

2. 组织点数管理
   - `GET /auth/org/points/members`
   - `POST /auth/org/points/adjust`
   - `GET /auth/org/points/records`

3. 模型扣点配置
   - `GET /auth/org/model-cost/list`
   - `POST /auth/org/model-cost/save`

4. 平台级组织管理
   - 组织列表、设置一级账号、查看成员、平台配点

5. AI 聚合代理
   - `POST /auth/ai-aggregate/proxy`
   - 允许代理 `/suno/` 路径
   - 已内置提交时扣点逻辑

6. Suno 音乐生成服务
   - 已存在 `SunoAudioGenerationService`
   - 已支持提交与查询任务
   - 但还没有现成的 `MinimaxMusic` 适配层

这些内容的使用原则必须固定：

1. 不修改 `ruoyi` 原项目文件
2. 不让本项目在运行时依赖 `ruoyi`
3. 只允许把可用代码复制到本项目后再调整优化
4. 复制后的代码、接口、表结构都归 `Creative Vision Music` 管理

### 5.2 为什么优先复制参考实现而不是直接接入原后端

最省工路径不是把新项目挂到 `ruoyi` 上，而是：

1. 音乐站前台独立开发
2. 后端也在本项目内独立搭建
3. 需要提速时，从 `ruoyi` 复制成熟实现到本项目

这样可以保留的价值是：

- 账号流程设计思路
- 组织结构设计思路
- 点数和扣费规则设计思路
- 代理 API Key 保密能力的实现思路
- 支付订单与回调处理的实现思路

需要额外补的最小改动：

- 若首版接入 `music-1.5 / music-2.0`
- 则需要在本项目中新增 `MinimaxMusicProvider`
- Suno 与海螺音乐的适配都应收敛到本项目自己的统一供应商接口

### 5.3 组织结构如何压缩到两级

现有系统支持 1 到 4 级组织账号，但你的项目只需要两层：

1. 一级账号
   - 音乐公司负责人
   - 可审批、配点、看全部成员

2. 二级账号
   - 公司下所有成员
   - 只能使用点数和查看自己的内容

实现上不建议照搬原项目整套组织系统，而建议：

1. 只复制需要的组织能力到本项目
2. 前台和业务规则只开放 1 级、2 级
3. 本项目内直接禁止创建 3 级、4 级入口
4. 入组时只允许映射为 2 级成员

这样更符合“独立项目、最小功能、最快上线”的要求。

## 6. 收费窗口的快速方案

### 6.1 两条收费路线

你已经明确了两条路线，这个方向是对的：

1. 组织路线
   - 平台向音乐公司负责人配点
   - 负责人向二级成员配点
   - 适合 B 端销售和线下签约

2. 线上直充路线
   - 用户自己充值资源包或购买会员
   - 适合 C 端自助转化

### 6.2 第一阶段建议的收费优先级

建议按下面顺序实施：

1. `最快上线`
   - 平台后台人工给组织配点
   - 负责人给成员配点
   - 个人用户先支持后台手动加点或激活码

2. `第二步`
   - 前台快速充值弹窗
   - 下单后跳转支付页
   - 支付成功后自动到账

3. `第三步`
   - 会员 + 资源包并行
   - 订阅积分 + 充值积分双账户

### 6.3 快速收费窗口建议形态

前台直接做一个不复杂的充值弹窗：

1. 当前余额
2. 本次生成预计消耗
3. 三档资源包
   - 9.9 元体验包
   - 29.9 元标准包
   - 99 元进阶包
4. 一个会员入口
   - 月卡
   - 季卡
5. 一个组织入口
   - 输入组织邀请码/组织码

### 6.4 为什么先做弹窗而不是完整会员中心

因为转化动作最短：

- 用户点击生成
- 余额不足
- 立即唤起充值窗口
- 支付后回到创作页继续生成

这比先做大而全的“个人中心 - 会员中心 - 套餐页”更快见效。

## 7. 支付侧现实判断

### 7.1 当前可参考的支付基础

在现有参考项目里已经能看到：

- 支付回调白名单配置
- 支付订单表 `chat_pay_order`
- 支付订单后台管理接口
- 支付宝 SDK 依赖

说明我们不需要从零摸索支付结构，但实现仍然应该落在本项目内。

### 7.2 当前缺口

目前还没有明确看到真正对用户开放的：

- 创建支付订单并拉起支付的前台接口
- 支付成功回填积分的完整业务链路

因此对于“快速收费窗口”，建议分两步：

1. 先落订单与到账规则
2. 再补真实支付拉起

如果需要最快试运营，甚至可以先做：

- 后台加点
- 激活码
- 企业线下打款后人工配点

而不是一开始就把在线支付当上线前提。

## 9. 最终建议

### 9.1 产品建议

不要把第一阶段目标写成“完整复制 Suno 全部能力”，而要写成：

`复刻 Suno create 页核心创作体验，并基于 AIZNT 的 Suno + 海螺音乐能力快速上线可收费版本。`

### 9.2 技术建议

最优路径是：

1. 前台新做音乐站页面
2. 后端在本项目内独立实现
3. 需要提速时，只从 `ruoyi` 复制成熟代码到本项目优化
3. 组织版先跑起来
4. 线上支付随后补齐

### 9.3 商业建议

先做能卖的，不先做大全套：

1. 企业组织配点
2. 用户充值资源包
